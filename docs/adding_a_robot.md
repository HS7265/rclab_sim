# 새 로봇 추가와 AI 작업 프롬프트

## 기본 원칙

다리 개수로 공통 코드를 분기하지 않는다. 모델에서 구조를 읽고 프로필에서 의미를 붙인다. 6족과 휴머노이드의 차이는 관절 수뿐 아니라 몸통 이름·부위 구성·구동 방식·초기 자세·지면 간격이다.

`profiles/hexapod.json`과 `assets/hexapod.xml`은 6개 다리 × 3개 모터 예제다. 이 예제를 실제 로봇의 관절 수나 축에 대한 정답으로 사용하면 안 된다.

## 1. MJCF 준비

모델 XML과 include, 메시, 텍스처를 로컬에 둔다. MJCF에 지면·조명·충돌 형상·관성·관절 제한·액추에이터가 정의되어 있어야 한다. 앱은 누락된 로봇 동역학을 추정하지 않는다.

URDF부터 시작한다면 MuJoCo의 [URDF 지원과 MJCF 모델링 문서](https://mujoco.readthedocs.io/en/3.11.0/modeling.html)를 참고한다. C++에서 `mj_loadXML`로 URDF를 읽은 뒤 `mj_saveLastXML`로 MJCF를 내보내는 준비 도구를 만들 수 있다. 이후 다음을 점검한다.

- `package://` 경로를 실제 메시 경로로 해석하고 파일의 단위·축을 확인한다.
- fixed joint 병합으로 링크 이름이 바뀌었는지 확인한다.
- 부동 베이스, 지면, 액추에이터, 충돌·마찰을 보완한다. URDF transmission이 원하는 MuJoCo 구동기를 자동으로 구성한다고 가정하지 않는다.
- 폐루프·링크 메커니즘과 차동 관계를 MJCF equality/tendon 등으로 검증한다.
- 메시가 보이는 것과 관성·구동 모델이 정확한 것을 구분해 검증한다.

원본 모델은 보존하고 별도 준비 모델을 만든다.

## 2. 프로필 작성

아래는 6족 예제 프로필의 축약 형태다. 실제 이름으로 교체한다.

```json
{
  "schema_version": 1,
  "name": "MyHexapod",
  "model": "../../my_robot/scene.xml",
  "base_body": "base_link",
  "controller": "pd",
  "adapter": "direct_motor",
  "control_dt": 0.002,
  "suspension": {
    "enabled": true,
    "height": 0.8,
    "quat": [1, 0, 0, 0]
  },
  "joint_defaults": { "kp": 10, "kd": 1 },
  "initial_positions": { "front_left_hip": 0.1 },
  "joints": {
    "front_left_hip": { "kp": 8, "kd": 0.8, "lower": -1.0, "upper": 1.0 }
  },
  "groups": [
    { "name": "Front left", "joints": ["front_left_hip", "front_left_knee"] }
  ],
  "contact_bodies": ["front_left_foot"],
  "recording": { "seconds": 120, "max_mib": 256 }
}
```

- `base_body`는 **로봇 몸통 링크**다. 모델의 첫 body/free joint를 고르면 안 된다. 공·물체가 먼저 나올 수 있다.
- 공중 고정을 사용하려면 해당 body에 free joint가 있어야 한다. 고정 베이스 모델은 고정 기능을 끄고 사용한다.
- `groups`에는 필요한 모든 다리·팔·몸통을 각각 등록한다. 같은 관절을 여러 그룹에 넣으면 오류다. 미분류 관절은 `Other / passive`에 표시된다.
- 관절·모터·qpos·qvel 순서가 같다고 가정하지 않는다. ball은 위치 4개/속도 3개, free는 위치 7개/속도 6개다.
- hinge 초기값/범위는 rad, slide는 m, quaternion은 **wxyz**다. GUI의 회전 목표값만 deg로 변환한다.
- 모델에 joint limit가 있으면 이를 사용한다. 프로필의 `lower/upper`는 무제한 관절에 대한 **GUI 작업 범위**다. 물리 관절 제한을 변경하지 않는다.
- 로봇의 물리 timestep이 0.004이면 `control_dt=0.002`를 사용할 수 없다. 같은 값 또는 정수배를 지정한다.
- 메시 단위나 관절 축 방향은 모델에서 바로잡는다. 표시에서 임의로 부호만 바꾸어 숨기지 않는다.

개인 경로가 들어간 프로필은 `profiles/local/my_robot.json`에 둔다. 이름을 잘못 적으면 초기화 중 명시적으로 실패한다.

## 3. 공중 높이와 자세 정하기

1. 초기 관절 자세로 모델을 계산하고 발·팔·몸통을 포함한 로봇의 충돌 형상 최저점을 확인한다.
2. 월드 Z가 위쪽인지, 바닥 높이가 얼마인지 확인한다. 경사지·지형이면 해당 위치의 지면을 사용한다.
3. 몸통 높이를 올려 **모든 로봇 충돌 형상이 지면과 떨어지도록** 충분한 간격을 둔다. 예제의 0.8m를 그대로 채택하지 않는다.
4. GUI에서 고정 높이와 방향을 확인한다. 관절 작업 범위에서도 발이 지면과 접촉하지 않는지 확인한다.
5. 고정 해제 시 중력이 작용하는지 확인한다. 고정 중 위치 오차는 5mm 이내를 초기 검증 기준으로 삼되, 자세·힘·모델 크기에 따라 실제 오차를 보고한다.

앱의 공중 고정 제약은 메모리의 모델에만 추가한다. 몸통과 월드를 연결하는 기존 고정 제약은 해제하고 로봇 내부 링크 제약은 남긴다.

## 4. 모터와 관절의 관계 확인

기본 제어는 `관절 목표 → 관절 PD 힘 → gain·gear를 반영한 ctrl`이다. `ctrl`은 항상 토크와 같은 단위라고 단정할 수 없다. 관절 힘, 액추에이터 입력, 실제 모터축의 각도/토크를 구분한다.

단일 모터가 hinge/slide 하나를 구동하면 기본 어댑터를 사용할 수 있다. 차동 모터·링크 구동·여러 모터의 공유 관절·서보·내부 상태 구동기는 C++ 어댑터가 필요하다. 위치뿐 아니라 속도와 힘의 변환을 함께 검증하며, 가능한 경우 `tau_joint·qdot = tau_motor·motor_dot`의 일관성을 확인한다. 알 수 없는 물리 모터각을 관절각과 같은 값으로 기록하지 않는다.

## 5. 완료 확인

```bash
./build/rclab_headless --robot profiles/local/my_robot.json --duration 0.2
./build/rclab_sim --robot profiles/local/my_robot.json
./build/rclab_sim --robot profiles/local/my_robot.json --self-test
```

- 표시되는 스칼라 관절·지원 제어 개수와 모델을 대조한다. 수동 관절까지 모두 모터로 세지 않는다.
- 작은 목표 변화로 축·부호·제한·힘 제한을 확인한 뒤 게인을 조정한다.
- 공중 고정/해제, GUI 그룹, 회전/직선 단위, 지원 불가 진단을 확인한다.
- 기록을 저장하고 동일 모델로 다시 열어 그래프 선택·3D 자세·시간 고정을 확인한다.
- 실제 보행은 제어기를 연결한 뒤 별도로 검증한다. PD 자세 유지 테스트를 보행 성공으로 보고하지 않는다.

이 저장소의 README.md, docs/adding_a_robot.md, docs/extensions.md와 AGENTS.md를 먼저 읽어라.

목표: [로봇 이름 / 6족·4족·2족·휴머노이드] 모델을 공통 C++ 시뮬레이터에 등록한다.

특수 구동 정보: [직접 구동 / 차동·링크 관계 자료 / 미확인]

먼저 모델을 조사해 아래 내용을 표로 보고하고 변경 계획을 제시하라.
1. 몸통과 free joint, 월드 축/단위, 지면, 관절 종류·축·범위·초기값
2. 관절·qpos·qvel·액추에이터의 실제 이름/주소 매핑
3. 모터와 관절의 전달 관계, 수동 관절, 내부 equality/링크 제약
4. 파일 경로 및 누락 자산, 제어 가능한 부분과 추가 어댑터가 필요한 부분

승인 후 profiles/local/[이름].json을 만들고 다리별/팔별/몸통별 GUI 그룹을 작성하라.
일반 로봇 추가에 공통 코어의 관절 개수나 로봇 이름 분기를 추가하지 마라.

특수 계산은 IActuationAdapter/IController 확장과 명시적 진단 채널로 작성하라.
실행 루프는 C++로 유지하고 모델·메시·개인 경로를 공용 저장소에 복사하지 마라.
원본 모델을 수정해야 한다면 원본을 보존하고 준비 모델의 변경 이유를 설명하라.

검증: CTest, 모델 로딩, 축/부호/단위, 목표값/힘 제한, 공중 고정·해제,
기록 저장·재개방, 그래프 시점 선택과 3D 자세 일치, 정지 중 카메라 이동.
성능은 계산 시간·주기 초과·실시간 배율로 측정하라.
실행한 명령과 결과를 제시하고 미검증 사항과 남은 제어기 연결을 명시하라.
작업 일지를 저장소 규칙에 맞춰 추가하라. 커밋/푸시는 별도 요청 전에는 하지 마라.
